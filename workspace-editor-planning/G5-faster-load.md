# G5 — Faster scene/resource open and editor startup (investigation + optimization)

**Effort:** M–L (front-loaded; A/B/C are the L portion, XL if implemented before the DocumentContext refactor and then reworked) · **Depends on:** soft on G1 (DocumentContext) for the clean expression of wins A/B/C

## Approach

**Measure-first, then rank-and-cut.** Both plans agree the GDStudio 7s→3s figure is **unverified hearsay** and that no optimization may be implemented before a reproducible `--benchmark-file` baseline exists on the user's real project.

- **Phase 1 (mandatory gate):** instrument the unmeasured hot seams using Godot 4.7's existing `OS::benchmark_begin/end_measure` (`--benchmark-file`, dumped at shutdown) plus the user's `objectdb_profiler` snapshot tool for object/resource allocation counts; capture 3 cold + 3 warm runs.
- **Phase 2:** implement wins strictly ranked by measured cost. Confirmed-in-code, highest-structural-value wins: **(A)** async/prefetched scene load (`load_scene` at editor_node.cpp:4880 is fully synchronous `ResourceLoader::load` + instantiate on the main thread); **(B)** lazy realization of restored scenes (`_load_open_scenes_from_config` at editor_node.cpp:6412 calls `load_scene` synchronously for EVERY previously-open scene, but only current_scene needs realizing at boot); **(C)** lazy/deferred main-screen plugin construction (ctor eagerly memnews CanvasItem/Node3D/ScriptEditor plugins ~9344 + ~50 add_by_type plugins in register_editor_types.cpp:225). Self-contained wins: theme/icon rasterization cache, thumbnail-worker throttle/parallelize, cold-import skip-unchanged audit, shader/pipeline cache warmth.

**Resolution bias:** ship A/B/C as pragmatic patches against flat EditorData now, but write them behind a thin per-document accessor seam so they become the natural API of the DocumentContext model rather than throwaway hacks — the explicit tech-debt-to-clean-architecture migration path.

## Ordered steps

0. **(gate) Build optimized tools editor + define the representative workload.** Build `target=editor`, production/optimized (NOT dev/debug — debug mis-ranks C++-bound vs I/O-bound phases). Pin down with the user: the representative project (size/asset count/scene complexity) and how many scenes they keep open on restore. No optimization begins until this gate passes.
1. **(gate) Instrument unmeasured hot seams with benchmark marks.** Today only Startup/Editor, Editor/First Scan, Editor/Load Scene are measured. Add unique-keyed begin/end pairs around: (a) load_scene phases — `ResourceLoader::load` (4880), `sdata->instantiate` (~4927), set_edited_scene/_load_editor_plugin_states tail (~4947-4956); (b) the ctor dock-build + each heavy add_editor_plugin (~9344) and the register_editor_types.cpp:225 add_by_type loop; (c) `_load_open_scenes_from_config` restore loop (6412); (d) EditorFileSystem `_first_scan_filesystem` (:317) and `reimport_files` (:3248); (e) EditorThemeManager "Register Icons"/"Generate Theme". **CRITICAL:** every begin needs a matching end on ALL early-return paths in load_scene (dependency/null-sdata branches ~4890/4902) — `benchmark_begin_measure` ERR_FAILs on duplicate keys and the map is flat (no nesting).
2. **Capture baseline + allocation snapshots, then rank.** Run `godot.editor --path <project> --benchmark --benchmark-file <abs>/bench_baseline.json`, 3 cold (cleared `.godot/imported` + shader cache) and 3 warm; record spread. Use `objectdb_profiler` (snapshot_collector.h, a snapshot tool NOT a timer) for object/Resource/Control counts after startup and after one scene open — a proxy for construction cost + a leak check. Sort marks descending. **This ranked JSON is the deliverable everything else is gated against; implement nothing absent from it.** Optionally render per-phase timings in the objectdb_profiler panel for in-editor iteration.
3. **WIN B (top startup win): lazy realization of restored scenes.** `_load_open_scenes_from_config` (6395) loops `load_scene(scenes[i])` for every restored path (6412), then `_set_current_scene` picks the active. With N restored docs this multiplies the full sync cost. Change: lightweight tab/placeholder per restored path, fully realize only current_scene at boot, realize others lazily on first tab activation (optionally warmed by background `load_threaded_request`). Biggest startup lever for users who keep many scenes open; directly gates multi-doc workspace-restore UX (G1–G4). Implement via a per-document `realize(path)` accessor so it becomes DocumentContext's API.
4. **WIN A: async/prefetched scene open.** `load_scene` calls `ResourceLoader::load(lpath, CACHE_MODE_REPLACE)` synchronously (4880), blocking on the full scene + sub-resources. Move only the I/O+parse (load + instantiate) to `ResourceLoader::load_threaded_request/get` on a worker (brief progress UI or tab-hover prefetch), then hand the finished root to the EXISTING synchronous tail (set_edited_scene + plugin edit) unchanged on the main thread. Quantify load vs instantiate vs plugin-edit from Step 1 first — if instantiate dominates, async I/O is moot and effort shifts to Node3DEditor gizmo/world setup. Gate behind an editor setting + A/B benchmark. Evaluate CACHE_MODE_REUSE only for same-session reopen where EditorFileSystem hasn't flagged the file changed.
5. **WIN C: lazy/deferred plugin construction.** Ctor eagerly memnews CanvasItem/Node3D/ScriptEditor plugins (~9344) building full 4-viewport 3D + 2D canvas UI; register_editor_types.cpp:225 eagerly add_by_type's ~50 plugins, many unused. Defer construction of the 3D editor (and AssetLib/audio/low-risk plugins first) until the relevant main screen is first selected or a document of that type opens; keep registration/menu/shortcut wiring eager so resolution doesn't break. Start with lowest-risk plugins before touching Node3DEditor (112 get_singleton call sites). Design pane-aware: this becomes per-DocumentContext plugin ownership.
6. **WIN D: theme/icon rasterization cache.** EditorThemeManager "Register Icons" (editor_theme_manager.cpp:189) rasterizes editor SVGs at scale every boot. Cache the rasterized atlas under the editor data dir keyed on a robust signature (engine version hash + scale/DPI + accent/base color + contrast); load on match, full-regenerate on miss or load failure. Self-contained, fixed cold-start cost independent of project size — most reliable measurable win, lowest merge risk.
7. **WIN E: thumbnail-worker throttle, then parallelize.** EditorResourcePreview runs a SINGLE worker thread (_thread_func:144) generating thumbnails serially, competing with scene open + FileSystemDock population. Higher-value/lower-risk half first: pause/lower-priority the preview queue while a scene open is in flight. Then (optional) move generation onto WorkerThreadPool group tasks (model on editor_file_system.cpp:3358), capping group size to avoid oversubscription. Measure perceived open with previews paused vs not.
8. **WIN F: cold-import + shader/pipeline cache audit.** Lower-ranked (cold/CI only). Verify `_update_scan_actions`/reimport skips files whose source+import md5 are unchanged; confirm reimport_files' WorkerThreadPool group task (:3358) uses all cores; check whether first Load Scene blocks on the WHOLE import queue vs only the target scene's dependencies (prioritize the latter). Separately confirm the editor shader/pipeline cache (RD or GLES3) is populated and reused across runs and isn't recompiling per scene open; add a mark around the first SubViewport/World3D draw. Mostly settings + cache-path verification.
9. **Synthesize ranked report; land wins incrementally.** For each implemented win, re-run the Step-2 harness and record before/after seconds. Keep only changes with measurable, reproducible improvement + acceptable merge risk. Deliverable: ranked table (win, mechanism, files, measured delta, merge risk). Ship as small independent patches. **Re-measure A/B/C AFTER the DocumentContext refactor lands** to confirm the rearchitecture didn't already obviate the micro-opts.

## Conflicts & resolutions

- **Data-model change: introduce DocumentContext now vs keep flat EditorData.** **Resolution:** pragmatic-first — prototype A/B/C against today's flat EditorData to deliver wins early, BUT implement them behind a thin per-document `realize()/accessor` seam whose signature is the future DocumentContext API. Tech debt: these patches WILL be reworked when DocumentContext lands. Migration: swap flat-EditorData accessors for DocumentContext methods with no call-site churn. **Do not introduce DocumentContext solely for G5** — let the multi-doc goal own that change.
- **Ranking: async open (A) vs lazy restore (B) as biggest win.** **Resolution:** do not hard-rank before Step 2 data — that's the point of measure-first. Provisional planning order: WIN B first (confirmed in code at 6412, lower-risk than async, multiplies with the multi-doc goal), then A, then C. Final order is whatever the baseline JSON shows; if instantiate dominates load, A drops and plugin/gizmo setup (C) rises.
- **Where the per-phase CPU timeline lives.** **Resolution:** optional, not critical-path. Use OS benchmark JSON as the primary low-effort instrument; add the in-editor ring-buffer panel only if iteration speed demands it; if added, put it in a SIBLING module rather than objectdb_profiler (which is snapshot-oriented). User decision below.
- **CACHE_MODE_REPLACE → REUSE for reopened tabs.** **Resolution:** adopt cautiously and measurement-gated — keep REPLACE on initial open + any scan_changes/file-modified flag; only consider REUSE for same-session reopen of a file not flagged changed. Low priority; only pursue if Step 2 shows reparse cost is material.

## Risks

- **GATING:** optimizing a non-bottleneck — the 7s→3s figure is hearsay, possibly project-specific import/thumbnail volume. *Mitigation:* Steps 0–2 are mandatory gates; never implement a win absent from the user's actual baseline; rank by measured seconds; treat 3s as a goal not a spec.
- Async load (A) reintroduces ordering bugs — plugins, `_set_main_scene_state` (call_deferred ~4874), editor_history assume full sync instantiation before set_edited_scene returns. *Mitigation:* move ONLY load/instantiate I/O to a worker; keep the realization tail synchronous on the main thread; gate behind a setting + A/B benchmark.
- Lazy plugin construction (C) breaks ~112 Node3DEditor::get_singleton()/CanvasItemEditor call sites assuming the singleton exists right after the ctor. *Mitigation:* keep registration/menu/shortcut wiring eager; defer only expensive subsystem setup; force-construct on first main-screen select or null-guard consumers; start with low-risk plugins.
- Lazy restored-scene realization (B) can desync scene-tab UI, current_scene, editor_history. *Mitigation:* realize placeholders with enough metadata; realize-on-activate runs the same code path as a normal open; validate restore + tab-switch + close across N scenes.
- Caches go stale (theme/icon on editor update or scale/DPI/color change; shader/pipeline on GPU/driver change). *Mitigation:* key on robust signatures; full-regenerate on any mismatch or load failure.
- Parallelizing thumbnails (E) can race the importer/ResourceCache or oversubscribe CPU. *Mitigation:* ship the throttle/pause-during-open half first; cap group size before true parallelism.
- Fine-grained marks: duplicate-key ERR_FAIL + flat map; a missed end on a load_scene early-return corrupts the dump. *Mitigation:* unique context:what keys; matching end on all early-return branches (~4890/4902).
- **TECH-DEBT:** pragmatic A/B/C patches get reworked when DocumentContext lands. *Mitigation:* write A/B/C behind a thin per-document realize/accessor seam; sequence them alongside/just after the refactor where feasible; accept some rework as the cost of earlier delivery; flag to user.

## Cross-goal dependencies

- **G1–G4 multi-document restore** opens MANY documents at once, multiplying load_scene cost — WIN B + WIN A directly gate multi-doc restore UX. Sequence so the DocumentContext refactor and these wins share implementation rather than double-work.
- A/B/C are most cleanly expressed on DocumentContext (owns scene root, World3D, EditorSelection, lazily-built per-pane plugins/docks + a realized/placeholder state). Prototype on flat EditorData but design the accessor seam for migration.
- **Per-document World3D (G1/3D wall):** WIN C's deferred Node3DEditor must be pane-aware; interacts with WIN F — multiple scenarios must SHARE compiled pipelines or each document open recompiles shaders.
- EditorFileSystem, FileSystemDock, EditorSettings stay project-global — WIN E/F must not be coupled to per-document state.
- objectdb_profiler is reused as the allocation-snapshot instrument; a per-phase CPU timeline panel may belong in a sibling module.

## Unresolved issues

1. What is the user's representative target project (size, asset count, scene complexity)? The Step-2 baseline is meaningless without the real workload. **NEEDS USER INPUT.**
2. Is the 7s→3s measured cold (empty import/shader cache) or warm? Determines whether caching (D/F) or scene-open/restore (A/B/C) is the dominant lever.
3. How many scenes does the user typically keep open on restore? Directly sets the magnitude of WIN B.
4. Which rendering backend — RD (Vulkan/D3D12) or GLES3? Determines whether WIN F touches shader_rd.cpp or shader_gles3.cpp.
5. Should benchmark marks ship permanently (gated by TOOLS_ENABLED) or live only on a local profiling branch? **USER PREFERENCE.**
6. Should the in-editor per-phase CPU timeline be built at all, and if so in objectdb_profiler or a sibling module? Optional; decide only if OS-benchmark JSON proves too slow to iterate on.
7. Is the DocumentContext refactor greenlit and sequenced before G5's A/B/C wins, or are pragmatic flat-EditorData patches acceptable interim with known rework cost? Determines whether A/B/C are M or XL.
